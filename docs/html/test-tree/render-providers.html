API contract (frontend tests rely on this; pinned by the backend tests)

Money values are JSON numbers (USD, float). Errors use the existing body {code, message}.

Batch creation POST /batches (multipart) gains data_class ("real" default | "demo") and confirm_demo ("true"). demo without confirm_demo=true is 422 VALIDATION_ERROR; any other data_class value is 422.

Batch JSON (all batch responses) gains: provider_id (string | null), data_class ("real" | "demo"), spent_usd (number, this batch's measured cost, 0 when none), pause_reason (null, "spend cap reached" or "provider not allowed for this data class"; only set while PAUSED).

List providers GET /batches/{id}/providers →

{ "data_class": "real"|"demo", "selected_provider_id": str|null,
  "any_selectable": bool, "message": str|null,            # message set when nothing is selectable
  "providers": [ { "id", "name", "kind", "data_rule",
      "setup": {"state": "ready"|"needs_setup", "reason": str|null},
      "estimate": null | {"seconds_per_video","batch_seconds","batch_cost_usd"},
      "estimate_label": "not measured yet" | null,        # label exactly this text when estimate is null
      "spend_cap_usd": number|null, "spent_usd": number, "remaining_usd": number|null,
      "selectable": bool,
      "refusal": null | {"code": "not_ready"|"data_class"|"over_credit", "reason": str} } ] }

Every registered provider is listed (the UI hides data_class refusals and greys not_ready).

Choose POST /batches/{id}/preview/approve accepts an optional JSON body {"provider_id": "<id>"}. Without a body the call behaves as today (batch keeps provider null = default provider). With an id the provider is checked and stored on the batch. Refusals leave the batch unchanged: 422 UNKNOWN_PROVIDER, 409 PROVIDER_NOT_READY, 409 PROVIDER_NOT_ALLOWED (C5), 409 PROVIDER_OVER_CREDIT. POST /batches/{id}/start re-checks a stored provider (ready, data class): 409 PROVIDER_NOT_READY / PROVIDER_NOT_ALLOWED; the batch stays DRAFT and no job is queued.

Change provider PUT /batches/{id}/provider {"provider_id"}: only DRAFT or PAUSED (else 409 INVALID_STATE), same refusals as above; QUEUED rows are enqueued again on the new queue.

Worker C5 behaviour (pinned): a demo-only provider with a real batch (API bypassed): the row is NOT rendered (still QUEUED, attempts 0, no TTS call), the batch goes PAUSED, outcome DEFERRED; pause_reason = "provider not allowed for this data class". Spend cap (pinned): worst case of one row = row_timeout_seconds × rate_per_second; the worker pauses (PAUSED, row stays QUEUED, outcome DEFERRED, reason "spend cap reached") when spent + worst > cap (equal is allowed). A completed row stores cost_usd = render_seconds × rate_per_second.

Code shape pinned by tests: vidgen.domain.providers (pure), vidgen.infrastructure.provider_registry (TOML), vidgen.infrastructure.queue.redis_heartbeat.RedisQueueHeartbeats, vidgen.services.provider_guard.ProviderGuard (RowRenderer(provider_guard=...)), Settings.providers_file, AppDeps.queue_heartbeats, JobQueue.enqueue_*(..., queue_name=None) and depth(queue_name=None) (queue_name passed only when the batch has a provider), StuckRow.provider_id with requeue_stuck_rows(..., provider_queues=). Registry TOML: [[provider]] tables with keys id name kind queue ai_mode data_rule spend_cap_usd rate_per_second|rate_per_hour requires_env; unknown keys are refused (so no token/secret keys).
